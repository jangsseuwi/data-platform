## 二、指标详情

### 1. 成交总额（GMV）

**业务含义**：当天实际到账的销售额，是收入侧最核心的指标。

**计算逻辑**

```sql
SUM(pay_amount) WHERE is_paid = 1 GROUP BY paid_date
```

**为什么按支付日期归属**

钱是支付那天到账的。如果按下单日期，一笔「11-30 下单、12-01 支付」的订单会被算进 11 月，
12 月的财务对账就对不上。

**包含**：当天支付成功的订单金额

**不包含**

- 取消订单（`order_status = 'cancelled'`）
- 未支付订单（`paid_at IS NULL`）
- 退款（本项目无退款表，真实业务必须扣减）
- 运费、优惠券抵扣（本项目无对应字段）

**已知问题**：无

---

### 2. 客单价

**业务含义**：平均每笔订单花多少钱。

**计算逻辑**

```sql
gmv / paid_order_cnt
```

**口径说明（重要）**

“客单价”有两种常见口径，本项目采用第一种：

| 口径       | 公式              | 含义                 | 本项目 |
| ---------- | ----------------- | -------------------- | ------ |
| 每单金额   | GMV ÷ 支付订单数 | 平均一单多少钱       | ✅     |
| 每用户金额 | GMV ÷ 支付用户数 | 平均一个买家花多少钱 | ❌     |

因为一个用户可以下多单，两种口径的结果不同。**对外沟通时必须说明用的是哪一种。**

**不包含**：同 GMV

---

### 3. 支付订单数 / 支付用户数

**业务含义**：订单数反映交易频次，用户数反映买家规模。

**关键区别**

```
一个用户下了 3 单 → 支付订单数 +3，支付用户数 +1
```

所以 `支付用户数 ≤ 支付订单数` 恒成立。如果哪天出现用户数大于订单数，
说明统计逻辑有 bug（比如忘记 `DISTINCT`）。

**不包含**：未支付、已取消的订单

---

### 4. 品类销售额 / 品类销量

**业务含义**：按品类拆分的销售结构，用于判断哪个垂类在拉动增长。

**计算逻辑**

```sql
SUM(sale_amount)  -- 销售额
SUM(sale_qty)     -- 销量（件数）
GROUP BY stat_date, category
WHERE is_paid = 1
```

**时间归属**：按下单日期（`created_date`），不是支付日期

> 注意：这里和 GMV 的时间口径**故意不同**。
> GMV 看“钱什么时候到账”（支付日），品类结构看“用户什么时候想买”（下单日）。
> 两者用途不同，不要求逐日对齐，但**月度合计应当相等**。

**不包含**：未支付、已取消订单的商品行

---

### 5. D1 / D7 / D30 留存率

**业务含义**：首购用户在特定时间点是否回来，衡量用户粘性。

**计算逻辑**

```sql
dN_users / cohort_users
-- dN_users = 首购后第 N 天有下单记录的用户数
-- cohort_users = 该首购日的用户总数
```

**三个关键定义**

| 项                       | 定义                                                  |
| ------------------------ | ----------------------------------------------------- |
| **cohort（分群）** | 按【首次下单日期】分组，不是注册日期                  |
| **Dn**             | 首购日 + N 个自然日，用 `DATEDIFF = N` 精确匹配     |
| **观察期**         | 只统计有足够观察天数的 cohort（排除最后 30 天的新客） |

**为什么按首购而不是注册分群**

本项目注册时间跨 2 年、订单只有 90 天。按注册分群会出现大量「注册了但从未下单」的空 cohort，
留存率被稀释成无意义的数字。

**为什么必须剔除观察期不足的 cohort**

最后 30 天的新客还没机会观察到 D30，算进去会把 D30 留存率拉低。
这是留存分析里最常见的错误。

**不包含**：注册后从未下单的用户（他们不在任何 cohort 里）

**已知问题**：模拟数据的留存曲线受 cohort 组成偏差影响，早期 cohort 偏高（详见 FAQ）

---

### 6. Top 商品销量

**业务含义**：每个品类内卖得最好的商品，用于选品和补货参考。

**计算逻辑**

```sql
ROW_NUMBER() OVER (PARTITION BY stat_date, category ORDER BY sale_qty DESC, sale_amount DESC)
```

**为什么分品类排名**

如果做全局 TopN，电脑和手机会包揽全部名次（单价高、销量也不低），
图书、食品这类低单价品类永远上不了榜，榜单失去「发现各垂类头部」的意义。

**排名并列的处理**：按 `sale_qty DESC, sale_amount DESC` 双键排序，保证结果可复现

**不包含**：未支付、已取消订单的商品

## 四、常见口径争议（FAQ）

**Q1：GMV 为什么不按下单日期统计？**

因为 GMV 衡量的是「收入」，收入以到账时间为准。按下单时间统计的是「成交意向」，
两者在跨月、跨天场景下差异明显。如果业务要看下单侧，请用「下单金额」这个独立指标，不要混用。

**Q2：复购率 64%，留存率只有 6%，矛盾吗？**

不矛盾。两个指标的时间粒度不同：

- 复购率：90 天窗口内下单 ≥2 次的用户占比（窗口宽，容易命中）
- 留存率：首购后**特定某一天**是否回访（单点，严格）

一个用户 90 天内买了 3 次，但都没落在 D1/D7/D30 这三天，就“贡献复购、不贡献留存”。

**Q3：为什么留存曲线随时间下降，越晚的 cohort 越低？**

这是 **cohort 组成偏差**：下单频繁的重度用户，首购时间天然靠前（数据窗口早期），
早期 cohort 里优质用户占比高；后期 cohort 剩下的大多是只买一次的长尾用户。

**Q4：品类销售额的日期口径和 GMV 不一样，会影响对账吗？**

按天会有差异（下单日和支付日不同），但月度合计应当一致。
如果月度都对不上，说明 DWS 层的支付过滤有问题，需要排查。

**Q5：Top 榜按销量还是销售额？**

两个榜单都要，但**分开呈现**。销量榜反映“大众选择”，销售额榜反映“营收贡献”，
同一个品类下两张榜的商品往往完全不同。

## 六、已知局限（模拟数据）

本项目数据为模拟生成，以下现象属于数据特征，不是计算错误：

1. **留存曲线偏平**：造数未建模“用户粘性随时间衰减”，D1/D7/D30 接近
2. **首末两天为边界数据**：已在 ETL 层做 T-1 截断，首日仍有支付延迟造成的偏差
3. **无退款、无运费、无优惠券**：真实业务的 GMV 口径需额外扣减
4. **商品名称为随机生成**：不影响指标计算，但看板可读性差

真实数据接入后，本节应当删除或更新。
