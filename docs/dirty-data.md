# 脏数据清单与对账记录

> 记录造数时**注入了哪些脏数据**，以及质量校验**是否全部抓到**。
>
> 这份文档回答一个问题：**我的数据质量规则到底有没有用？**
> 如果规则能抓出 1000 条，而实际注入了 1000 条，说明规则有效；
> 抓出 800 条，说明漏了；抓出 1200 条，说明规则误报。

| 项 | 内容 |
|---|---|
| 造数脚本 | `etl/gen_data.py` |
| 规模 | 100,000 个订单（注入后 100,300 行） |
| 随机种子 | 42（固定，保证可复现） |
| 校验脚本 | `quality/check.py` + `quality/rules.yaml` |
| 最后对账 | 2026-11-27 |

---

## 一、为什么要故意造脏

如果直接用公开的干净数据集：

- 质量规则没有素材，**跑出来的报告是 0 异常**，看不出规则是否有效
- 无法验证「清洗逻辑」到底清洗了什么
- 面试时讲不出「我处理过什么数据问题」

**造脏数据，是为了让校验有靶子。**

每条脏数据在注入时就知道「期望被哪条规则抓到」，这样校验结果才能被验证——
这叫 **可对账**（reconcilable）。

---

## 二、注入清单

| # | 类型 | 注入方式 | 比例 | 条数 | 期望被哪条规则抓到 |
|---|---|---|---|---|---|
| 1 | 用户为空 | `user_id` 置 NULL | 1.0% | 1,000 | ODS-001 非空校验 |
| 2 | 金额为负 | `pay_amount` 取反 | 0.5% | 500 | ODS-002 值域校验 |
| 3 | 订单号重复 | 复制整单（含明细） | 0.3% | 300 | ODS-003 唯一性校验 |
| 4 | 状态越界 | `order_status` 改为 `unknown` | 0.2% | 200 | ODS-004 枚举校验 |
| 5 | 时间穿越 | `paid_at` 调到 `created_at` 之前一天 | 0.1% | 100 | ODS-005 时序校验 |

### 设计要点

**① 互斥抽样**

五类脏数据**不重叠**（用 `used` 集合保证），所以每类的命中数**精确等于** `总数 × 比例`。

如果允许重叠，一行既没 `user_id` 又是负数，则「非空异常 1000 + 负金额 500」加起来
会大于实际异常行数，**报告数字无法与注入量对账**。

**② 重复订单最后做**

它复制的是「已经注入过脏数据的行」，所以副本也会带着原有的脏。
这更接近真实世界——上游重跑导致的重复，脏的和干净的都会重复。

**③ 固定随机种子**

`random.seed(42)` + `Faker.seed(42)`，每次造出完全相同的数据。
这样改了规则后，报告数字的变化能明确归因到**规则**，而不是「这次随机结果不一样」。

## 三、对账结果

### 3.1 质量规则抓取情况

| 规则 ID | 规则 | 注入 | 抓到 | 结果 |
|---|---|---|---|---|
| ODS-001 | user_id 非空 | 1,000 | 1,000 | ✅ 完全匹配 |
| ODS-002 | 金额非负 | 500 | 500 | ✅ |
| ODS-003 | 订单号唯一 | 300 | 300 | ✅ |
| ODS-004 | 状态枚举 | 200 | 200 | ✅ |
| ODS-005 | 支付时间不早于创建 | 100 | 100 | ✅ |

**五条全部精确匹配，健康分 100%。**

### 3.2 清洗层的数据变化

| 指标 | 行数 | 说明 |
|---|---|---|
| `ods.orders` | 100,300 | 原始 + 300 条重复 |
| `dwd.fact_order` | 98,200 | **丢弃 2,100 行** |
| 差异 | 2,100 | = 1,800 丢弃（1,000+500+200+100）+ 300 去重 |

> 这个等式成立，说明清洗没有多丢也没有少丢。
> 即使某条订单「既重复又带脏」，两种口径算出来的差额依然相等——
> 因为每个缺陷恰好对应一行的消除。

## 四、未被覆盖的脏数据类型

以下问题**真实业务中常见，但本项目没有注入**，属于已知缺口：

| 类型 | 例子 | 影响 | 备注 |
|---|---|---|---|
| 上游重复推送 | 同一批数据一天推 5 次全量 | ODS 严重膨胀 | 本项目的重复是「单条复制」，不是「整批重推」 |
| 手机号格式混乱 | `138-0000-0000` / `+8613800000000` / `13800000000` | 无法关联用户 | `ods.users.phone` 未标准化 |
| 城市写法不一致 | 「哈尔滨市」vs「哈尔滨县」 | 分组统计被拆散 | 数据视图已发现，见下方 |
| 金额精度 | `0.1 + 0.2 != 0.3` | 对账差几分钱 | 已用 DECIMAL，但上游若传 float 仍会引入误差 |
| 字符串带空格 | `' 张三'` vs `'张三'` | 分组出现两个「张三」 | `dim_user` 已做 TRIM 兜底，但其他字段没有 |
| 字符编码错误 | 中文变问号 | 展示乱码 | 已统一 utf8mb4，但上游传错仍会乱 |
| 跨天支付 | 23:59 下单、00:01 支付 | 归属日期不同 | 已通过「按支付日归属 GMV」处理 |
| 维度表延迟 | 订单先到，用户维度后到 | JOIN 丢数据 | 本项目的维度是全量同步，不存在延迟 |

### 一个已发现但未修复的问题

`ods.users.city` 存在「哈尔滨市 / 哈尔滨县」这类**同一地点的不同写法**，
导致「城市用户榜」把同一个城市拆成两行。

真实项目的解法是建一张**城市映射表**做标准化，这属于「数据标准管理」的范畴，
是数据治理岗的核心工作之一。本项目暂未实现，记为待办。

## 五、如何复现

```powershell
# 1. 重新造数（固定种子，结果与本次完全一致）
python etl/gen_data.py --orders 100000

# 2. 重跑整条链路
python scripts/run_pipeline.py --skip-gen

# 3. 看质量报告
#    终端会打印对账表，同时生成 docs/quality-report.html
```

如果重跑后数字与本文档不一致，说明：
- 造数参数变了（`--orders` 或 `--seed`）
- 或 `DIRTY_RATE` 被修改过

**两种情况都应该同步更新本文档。**

## 六、这份文档的用途

| 读者 | 关心什么 |
|---|---|
| 你自己（三个月后） | 为什么当初这么造数、数字对不对 |
| 面试官 | 你有没有「验证规则有效性」的意识 |
| 接手的人 | 改了清洗逻辑后，怎么回归验证 |

面试时可以这样讲：

> 我造了 10 万单，按 5 类脏数据各注入固定比例，然后写质量规则去抓。
> 注入 1000 条空用户，规则抓出 1000 条，五类全部对上——这样才能证明规则有效，
> 而不是「写了几条 SQL 跑出几个数字」。
